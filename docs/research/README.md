# Build EEganizer's design toolkit on pystitch

EEganizer can ship a credible "view, inspect, convert, light-resize, send to machine" feature on top of one open-source engine: **pystitch**, the Ink/Stitch team's MIT-licensed, actively maintained fork of pyembroidery. It reads about 40 machine formats (including PES v1–v10, DST, JEF, EXP, VP3, HUS and XXX), writes 11, renders PNG/SVG thumbnails with no dependencies, and exposes every property a details panel needs. MIT permits closed-source commercial use on the server and in the browser, provided the notice ships with the code. What open source cannot deliver matters just as much. **No open library does stitch-aware (density-preserving) resizing**: every candidate scales coordinates, and stitch density shifts with them. **No open library reads Bernina ART or Wilcom EMB**, and none of the parsers has been fuzzed for hostile uploads. The JavaScript and Rust ecosystem is young and thinly adopted, so it is a good source of in-browser preview code but a poor primary dependency. The competitors are vendor-locked clouds (Brother Artspira, mySewnet, Wilcom Workspace) and $65–$180 desktop tools, so EEganizer's differentiation is a **vendor-neutral library that previews, fit-checks and converts in place**, not an editor. The recommended path has three phases. Phase 1 runs server-side pystitch in a sandboxed worker for thumbnails, properties and conversion. Phase 2 adds guarded resize (a small scale band, long-stitch and density warnings) and hoop-fit checks. Phase 3 is optional: an in-browser viewer, and possibly a licensed commercial API (Wilcom EWA) if customers demand true recalculated resizing.

## Only one maintained, permissive engine covers the formats customers actually own

The format logic in this field comes from a small family of codebases. The other candidates are ports of it or are unsuitable.

| Project | License | Runtime | Formats | Maintenance (as of Oct 2026) | Verdict |
|---|---|---|---|---|---|
| **pystitch** (inkstitch org) | MIT | Python ≥3.9, pure Python | Reads ~40, writes 11 (.dst .exp .gcode .jef .pec .pes .sew .tbf .u01 .vp3 .xxx) | v1.0.1 on 2026-06-19; commits through Sep 8, 2026; 112 stars | **Primary engine** |
| pyembroidery (EmbroidePy) | MIT | Python, no deps | Same family; writes ~10 | Last release 1.5.1 on 2024-03-27; single maintainer; 312 stars | Dormant upstream; use the fork |
| libembroidery (Embroidermodder) | zlib | C single header | Claims "over 45" formats; no current per-format table | Self-labelled `v1.0-alpha`; commits Jul 2026; 82 stars | Too immature for untrusted input |
| Ink/Stitch | GPL-3.0 | Inkscape extension | Uses pystitch for I/O | v3.3.0 on 2026-07-31; ~1.4k stars | Not a library; nothing extra needed |
| Ricuci / embroidery-converter-kit | MIT code, CC BY docs, trademarked name | TypeScript, zero deps | Reads 13, writes 10 incl. HUS, VIP, ZHS | First published 2026-07; 1 star | Watch; audit before any use |
| tsembroidery | MIT | TypeScript | Reads/writes .pes .dst .jef .exp .vp3 .xxx; SVG out | 2.9.0, very active since 2025-05 | Candidate for browser preview |
| oxideav-embroidery | MIT | Rust | Broad decode; VP3 header-only, PES write minimal | 0.0.3; 249 downloads | Experimental; only fuzzed option |
| Embroidery Reader | GPL-2.0 | C# | PES only | No releases | Not suitable |

**pystitch** is the clear choice. Its README calls it "an updated fork of the original" pyembroidery, and its recent commits come from Ink/Stitch maintainers. They include a September 2026 PEC fix ([GitHub](https://github.com/inkstitch/pystitch), [commits](https://github.com/inkstitch/pystitch/commits/main), [PyPI](https://pypi.org/pypi/pystitch/json)). Upstream pyembroidery has had **no commits since March 27, 2024**. All of its recent work came from one maintainer ([commits](https://github.com/EmbroidePy/pyembroidery/commits/main), [PyPI](https://pypi.org/pypi/pyembroidery/json)). The libembroidery README is labelled "Under construction, please wait for v1.0 release" ([README](https://raw.githubusercontent.com/Embroidermodder/libembroidery/main/README.md)). That rules it out as the first parser to touch internet uploads. The TypeScript and Rust ports are real and moving fast. Ricuci calls itself "the first open implementation of a ZHS writer," and oxideav ships a libFuzzer suite. But both are months old, with one or two stars, so they serve as references rather than foundations ([Ricuci](https://github.com/Federicokalik/embroidery-converter-kit), [oxideav](https://github.com/OxideAV/oxideav-embroidery), [tsembroidery](https://registry.npmjs.org/@guillaumemmm/tsembroidery)). The pyembroidery family is also a good fit for this codebase, because the Library Setup Agent is already written in Python.

The pyembroidery family reads the requested formats well, with known caveats. PES reading branches on every header from `#PES0001` to `#PES0100`. For unknown versions it falls back to the embedded PEC stitch block ([PesReader.py](https://raw.githubusercontent.com/EmbroidePy/pyembroidery/main/pyembroidery/PesReader.py)). PES **writing is limited to version 1 or 6** ([PesWriter.py](https://raw.githubusercontent.com/EmbroidePy/pyembroidery/main/pyembroidery/PesWriter.py)), so converted PES files lose newer PE-Design object data. HUS decodes through a pure-Python EmbCompress implementation that "does not require any compiled element or dll file" ([pyembroidery](https://github.com/EmbroidePy/pyembroidery)). HUS and VIP output exist only in the young Ricuci and oxideav projects. The ART reader entry is **commented out** in pyembroidery's source ([EmbPattern.py](https://raw.githubusercontent.com/EmbroidePy/pyembroidery/main/pyembroidery/EmbPattern.py)), and ART support exists only in proprietary tools such as Wilcom and Hatch ([Wilcom](https://help.wilcom.com/portal/en/kb/articles/supported-formats), [Hatch](https://help.hatchembroidery.com/portal/en/kb/articles/what-file-formats-does-hatch-embroidery-v2-v3-read-and-write)). Native object formats such as Wilcom EMB, Bernina ART, mySewnet EDO and Janome JAN are software working files that "are not meant to run directly on machines" ([emborado](https://www.emborado.de/en/glossary/embroidery-file-format)). EEganizer should store them and label them "preview unavailable," and should not promise to convert them. The project's own README warns that conversion "is always lossy" ([PyPI](https://pypi.org/project/pyembroidery/)). An early pyembroidery PES writer once produced files that showed blank in Brother software ([PyPI 1.0.0](https://pypi.org/project/pyembroidery/1.0.0/)). Every output format therefore needs a physical stitch-out test before it is offered to customers.

## The properties panel is cheap, and the resize feature has to be honest

pystitch's `EmbPattern` model already provides what an inspection panel needs. That covers `bounds()` for size, `count_stitches()`, `count_color_changes()`, `count_stitch_commands()` for trims and jumps, `get_unique_threadlist()` for thread colours with brand and catalog data, and `get_metadata()`, which records the PES version ([EmbPattern.py](https://raw.githubusercontent.com/EmbroidePy/pyembroidery/main/pyembroidery/EmbPattern.py)). It also has built-in `write_png` and `write_svg` with a "fancy" shaded mode, needing no image libraries ([PngWriter.py](https://raw.githubusercontent.com/EmbroidePy/pyembroidery/main/pyembroidery/PngWriter.py)). EEganizer must compute two values itself, because no library provides them. **Estimated stitch time** is stitch count divided by machine speed, plus a fixed allowance per colour change. **Hoop fit** compares the design bounds with a hoop table. Fit checks need the usable sewing field, not the nominal hoop size. A Brother 4×4 hoop sews about 3.93 in, and users report nominal-4-inch designs being rejected ([Inkscape forum](https://inkscape.org/it/forums/embroidery/solving-the-pattern-is-too-large-for-frame)). Hatch Organizer sells on "522 hoop presets" ([Hatch](https://www.hatchembroidery.com/pricing)), which shows that a curated hoop table is a real data asset. Colour needs a UI caveat. DST carries no thread colours ([Brother manual](https://support.brother.com/g/s/hf/htmldoc/hsm/om/888p5x/en/10_01.html)), and PES stores palette indices into Brother's thread table rather than RGB values ([EduTechWiki PEC](https://edutechwiki.unige.ch/en/Embroidery_format_PEC)). A DST file converted to PES or JEF will show default colours, and the interface should say so.

Resizing is where an honest product differs from a misleading one. A stitch file is a list of needle positions. Wilcom explains that enlarging a DST increases "stitch spacing … without any adjustment to the stitch count" ([Wilcom blog](https://productblog.wilcom.com/?p=5321)). Enlarging therefore leaves gaps. It can also push stitches past the **12.1 mm DST limit**, which triggers automatic trims and missing sections ([zdigitizing](https://zdigitizing.com/how-to-properly-resize-embroidery-designs/), [EduTechWiki DST](https://edutechwiki.unige.ch/en/Embroidery_format_DST)). Shrinking packs stitches together and breaks thread. Every open-source candidate scales by coordinate math alone, and pystitch states that "high-level shape and fill processing is explicitly out of scope" ([pystitch](https://github.com/inkstitch/pystitch)). Commercial tools do the harder job in one of three ways. Embrilliance recalculates stitches heuristically across 50–250% ([Embrilliance](https://embrilliance.com/product/essentials)). mySewnet separates density-preserving "Resize" from plain "Scale" ([mySewnet help](https://softwarehelp.mysewnet.com/MSW/100/Embroidery/Topics/Resize_and_Scale.htm)). Wilcom and Hatch convert stitches back into objects, and Wilcom admits that "not all objects will be restored" ([Wilcom docs](https://docs.wilcom.com/embroiderystudio/28/en/OnlineHelp/Quality/functions/functions-9.htm)). pystitch does provide one useful safeguard. Its writers split stitches that exceed each format's maximum stitch length, using a configurable `long_stitch_contingency` ([pyembroidery](https://github.com/EmbroidePy/pyembroidery)).

The practical rule is to offer **plain proportional scaling labelled "small adjustments,"** never "recalculation." EEganizer should show a soft warning beyond about ±10% and a hard warning beyond about ±20%. It should also report the longest stitch and the change in density (stitches per area) after scaling, and block free-standing lace entirely. That band is folk wisdom; no reachable source states a fixed percentage. Digitizers go further and advise keeping the purchased size ([OML Embroidery](https://omlembroidery.com/resizing-stitch-files-yay-or-nay)), so the warning copy should be validated with real test stitch-outs.

## MIT and zlib clear the licensing bar, and GPL and AGPL stay out of the browser

| License | Server-only SaaS | Code shipped to the browser (JS or WASM) |
|---|---|---|
| MIT (pystitch, pyembroidery, tsembroidery, Ricuci core) | No obligations | Keep the copyright notice in the bundle (minifiers strip comments) |
| zlib (libembroidery) | No obligations | Do not misrepresent origin; mark altered versions |
| GPL-2/3 (Ink/Stitch, Embroidery Reader) | No obligations, even if modified | Shipping the code counts as conveyance, and the client bundle then falls under the GPL |
| AGPL-3 | Modifying the code requires offering source to all network users | Avoid |
| ACSL (PEmbroider) | Restricts commercial use | Avoid |

The license texts confirm MIT for both pyembroidery and pystitch ([pyembroidery LICENSE](https://raw.githubusercontent.com/EmbroidePy/pyembroidery/master/LICENSE), [pystitch LICENSE](https://raw.githubusercontent.com/inkstitch/pystitch/main/LICENSE)). pystitch's PyPI metadata has no license classifier, so the repository's LICENSE file is the authoritative statement. libembroidery permits use "for any purpose, including commercial applications" ([LICENSE.md](https://raw.githubusercontent.com/Embroidermodder/libembroidery/main/LICENSE.md)). Ink/Stitch is GPL-3 ([LICENSE](https://raw.githubusercontent.com/inkstitch/inkstitch/main/LICENSE)). Under GPLv2 and v3, running software as a SaaS is not "conveying" ([Black Duck](https://www.blackduck.com/blog/agpl-affero-gpl-3.html)). EEganizer still gains nothing from Ink/Stitch, because its format layer is MIT-licensed pystitch. Several projects carry no license at all, including manthrax/dst-format, HoangEditor/embroidery-converter and twineconvert ([dst-format](https://github.com/manthrax/dst-format)). Their code is off-limits until the authors grant one. MIT and zlib carry no patent grant. No embroidery-format patent assertions were found, but counsel should note the gap. The GPL FAQ was quoted from secondary sources only and should be confirmed against gnu.org.

The bigger legal exposure is the content, not the code. Designer licenses forbid sharing, but some explicitly permit format conversion for the buyer's own use. Creative Fabrica is one example ([Creative Fabrica](https://creativefabrica.com/de/single-sales-license)). Others bar redistribution "in any format" ([Creative Appliques](https://creativeappliques.com/?p=240337)). EEganizer should limit conversion outputs to the owning account, offer no public links, add a terms-of-service warranty that the user holds the rights, and run a DMCA takedown process. Parsing unencrypted files with an independently written open-source reader is lower risk than doing its own reverse engineering. Both the US (§1201(f)) and the EU (Software Directive Art. 6) have interoperability exceptions, but courts read them narrowly ([govinfo §1201](https://www.govinfo.gov/content/pkg/USCODE-2024-title17/html/USCODE-2024-title17-chap12-sec1201.htm), [Directive 2009/24/EC](https://www.legislation.gov.uk/eudr/2009/24/article/6)). The hard line is **never to decrypt encrypted vendor designs**: mySewnet subscription designs are encrypted and tied to an active subscription ([mySewnet](https://www.mySewnet.com/en-us/crafting/crafting-in-library)). EEganizer should detect such files and store them unopened. All of this needs counsel's sign-off.

## Vendor clouds lock customers in, and no neutral library exists

The cloud competitors are each tied to one brand and offer small consumer quotas. Brother Artspira gives about 20 cloud files free and about 100 with Artspira+ ([Brother](https://support.brother.com/g/s/hf/mobileapp_info/artspira/plan/en.html)), which launched at $12.99/month ([press release](https://seekingalpha.com/pr/19482627-brother-expands-inspiration-with-the-introduction-of-artspira-a-subscription-plan-offering)). mySewnet Cloud offers 100 MB ([mySewnet](https://mysewnet.com/products-and-plans/one-purchase)). The closest functional rival, **Wilcom Workspace Library**, is browser-based with 10 GB, but it targets "embroidery businesses and teams" ([Wilcom](https://wilcom.com/workspace/library)). The hobbyist organizers are one-time-license desktop or mobile apps. SewWhat-Pro costs about $65, Embrilliance Essentials $139–$159 and Hatch Organizer about $149 ([machineembroiderygeek](https://www.machineembroiderygeek.com/?p=20167), [Embrilliance](https://embrilliance.com/product/essentials), [Techjockey](https://www.techjockey.com/compare/sewiconz-vs-hatch-embroidery)). StitchBuddy's free tier caps saving at 1,000 stitches ([App Store](https://apps.apple.com/us/app/-/id522499369)). Free online converters already commoditize basic conversion. The Google Workspace "Embroidery Viewer and Converter" handles PES, DST, EXP, JEF, VP3, U01 and PEC, and its output set matches pyembroidery's writers, which suggests (unverified) that it is built on it ([Workspace Marketplace](https://workspace.google.com/marketplace/app/embroidery_viewer_and_converter/397239404956)). So customers will not pay for conversion alone. What they lack is a cross-brand library where every stored file already has a preview, a properties sheet, a fit check against their own machine, and one-click export. The competitor scan was incomplete: Embird, Floriani, Janome's cloud and Pulse were not checked.

The only commercial alternative found is **Wilcom's Embroidery Web API**. It is a REST/XML service for TrueView rendering, EMB editing, auto-digitizing and conversion, sold through subscription App ID/App Key plans with no public pricing ([Wilcom EWA](https://help.wilcom.com/portal/en/kb/wilcom-international/embroidery-api), [getting started](https://help.wilcom.com/portal/en/kb/articles/ewa-api-getting-started)). It centers on EMB and adds per-call cost and vendor dependency. It is worth evaluating only if customers demand photoreal renders or object-based resizing.

## Recommended architecture: server-first pystitch, browser later

**Run pystitch server-side first.** It is pure Python and the most complete engine, and server-only use avoids even the MIT notice obligation in client bundles. Parse every upload in an isolated worker with CPU-time, memory and output-size limits and per-file timeouts. pystitch only began raising explicit `IOError`s instead of silently ignoring errors in 1.5.0 ([pystitch](https://github.com/inkstitch/pystitch)). No CVEs, OSS-Fuzz integration or published fuzzing exist for any Python, C or TypeScript candidate. A short in-house fuzzing pass, for example with Atheris, before launch is cheap insurance. Thumbnails and the properties JSON should be generated once at ingest and cached next to the file, so library browsing never re-parses anything.

**Treat the browser as an optional later layer.** Pyodide could run pystitch unchanged in a Web Worker, but the first load costs roughly **5–7 MB and 0.5–1.3 s** to initialize, based on Pyodide 0.23-era benchmarks ([Pyodide blog](https://blog.pyodide.org/posts/0.23-release/)). No public pystitch-in-Pyodide demo was found. A small TypeScript reader such as tsembroidery, or an audited fork of Ricuci's core, could power an interactive zoom-and-pan viewer. Conversion should stay on the server. Browsers cannot write to USB sticks directly: Chrome blocks the mass-storage class from WebUSB ([Chromium blink-dev](https://groups.google.com/a/chromium.org/g/blink-dev/c/LZXocaeCwDw/m/GLfAffGLAAAJ)). Getting a file onto the machine therefore means a plain download, optionally a Chromium save picker aimed at the USB drive, plus help text. Brother and Bernina sell Wi-Fi transfer, but it is vendor-locked ([Artspira](https://www.brother-usa.com/apps/sewing-embroidery/artspira), [Bernina WiFi Device](https://softwarehelp.bernina.com/en/MainHelp/PART_Processing/network/network-15.htm)). The one open precedent, Respira, sends PES to a Brother SKiTCH over WebBluetooth ([Respira](https://github.com/jhbruhn/respira)).

| Phase | Scope | Engine | Key guardrails |
|---|---|---|---|
| **1 — View and convert** | PNG/SVG thumbnails at ingest; properties panel (size in mm and inches, stitches, colours, trims, jumps, thread list, PES version); convert to PES, DST, JEF, EXP, VP3, XXX, U01 and PEC; download for USB with machine-appropriate names | pystitch in a sandboxed server worker | Owner-only outputs; "preview unavailable" for ART, EMB, encrypted or unknown files; DST colour caveat; stitch-out validation per output format |
| **2 — Fit and light resize** | Machine profile per customer; hoop-fit check against usable sewing fields; thread chart and colour-sequence printout; stitch-time estimate; proportional scale, rotate and mirror | pystitch transforms plus in-house hoop table | Warnings beyond ±10% and ±20%; longest-stitch and density report; FSL block; original file always kept |
| **3 — Richer experience** | In-browser interactive viewer with stitch-order playback; optional HUS and VIP output; evaluate Wilcom EWA for recalculated resizing and TrueView renders | tsembroidery or audited Ricuci fork; vendor API | MIT notices in the bundle; vendor contract review for data handling |

Merge, split, lettering and true density recalculation are deliberately left out. They are what customers pay Embrilliance and Hatch for, and doing them well requires proprietary heuristics that open source does not provide.

## Conclusion

The open-source picture is better than "nothing exists" and narrower than "anything is possible." One maintained MIT engine makes reading, rendering and converting the mainstream home-machine formats a matter of engineering effort, not research. The parts customers value most at the high end, density-preserving resizing and native-format editing, remain proprietary. EEganizer's advantage therefore lies in the organizing layer around the engine: properties precomputed at ingest, a curated hoop table matched to each customer's machine, and honest resize guardrails. Free converters and vendor clouds offer none of these together. Two dependencies need active management. pystitch's health rests on the Ink/Stitch team, so EEganizer should pin versions and keep the ability to fork. The absence of any fuzzing makes the parsing sandbox a requirement, not an option. If customers later push for real resizing, the decision is "license Wilcom's API" versus "go without," not "build it in-house." That choice can wait until Phase 2 usage data shows how often customers resize beyond the safe band.
